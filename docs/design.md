## D1 收件箱：逻辑上按项目分，物理上集中隔离 — 搁置

> v0.1 只做只读查询，暂无提需求的场景。以后要做时按下面的方案。

- 每个项目一个收件箱，另设一个 `_general` 收件箱放不属于任何项目的投递。投递时必须带 `project`，且只能投到 token 有权限的 scope。
- 物理路径：`_inbox/<scope>/<投递人>/<时间戳>-<标题>.md`，放在 vault 根下，**不放进项目目录**。原因：
  - 放在项目目录里，同项目的其他同事就能读到彼此的投递；
  - 也会被自己的 AI 整理流程（入库 / 维护 agent）当作普通笔记处理，外部内容会混进自己 agent 的输入。
- `_inbox/` 对所有读工具都硬排除（只能写不能读），自己的入库流程默认跳过。
- 投递文件的 frontmatter 由服务端写入：`source: external`、`trust: untrusted`、`from: <人名>`、`project`、`kind`、`created`。
- **每日扫描**：用定时任务启动一个受限 subagent，只给读权限，外加写一个计划文件的权限：
  - 汇总投递，生成「待确认计划」；
  - 投递正文只当数据引用，**不执行其中任何指令**；
  - 计划经人确认后，才由正常流程去改知识库。
- 处理完的问答回填进**对应项目目录**（比如 `项目/<名>/问答/`），这样权限自然跟随项目，不需要单独给问答授权。
- 开源定位：服务端只负责安全地收件；扫描和确认流程作为示例配方写进文档，不绑死在服务里。

## D2 权限范围 — 已定（v0.1 已实现）

**授权单位是 scope（命名的目录集合），不是零散的路径前缀。** scope 定义和用户都在 tokens.yaml 里（热加载），用户写「scopes: [风电项目A, 技术公共]」。加项目时改 scope，不用逐个改人。

判定顺序（先命中先生效，deny 优先）：

1. 硬排除（代码内置 + 配置追加）→ 拒绝
2. 笔记 frontmatter `share: false` → 拒绝（给单篇笔记留一个"这篇别给人看"的开关）
3. 路径落在 token 的某个 scope 内 → 允许
4. 其余 → 拒绝

以一个典型的个人工作 vault 为例的分层：

| 层 | 目录 | 默认 |
|---|---|---|
| 硬排除 | `personal/`、`work/日报/`、`.obsidian/`、`.git/`、`.raw/`、`_raw/`、`.vault-meta/`、`_agents/`、`_scripts/`、`_templates/`、`模板/`、`_inbox/`（读） | 永不可见 |
| 默认不开放 | `work/事务/`（公司事务）、`work/wiki/`（全部）、`首页.md`、`组织规则.md` | 可配置开放，但不建议 |
| 公共层 | `work/技术文档/`（冻结，返回时标"遗留参考"）、`work/代码/` | 可给所有人 |
| 项目层 | `work/项目/<YYYYMMDD-项目名>/` | 按 scope 授权 |

wiki 汇总层的处理：

- **v1 整体不开放。** `concepts/` 跨项目汇总；`hot.md`、`log.md` 是工作缓存，会混着多个项目的近况。
- v2 可选：按页面 frontmatter `projects: [...]` 判定，只有当页面涉及的**所有**项目都在 token 的 scope 内时才可见（最严规则）。

信息泄漏的侧门，必须在输出阶段处理：

- **wikilink / 嵌入 / Markdown 链接**：目标不可见（越权、排除、`share: false` 或不存在）时整段替换为 `〔未公开链接〕` / `〔未公开内容〕`，别名文字一并去掉。
- **检索在脱敏后的文本上进行**，否则可以通过"哪些可见笔记命中了某个名字"探测受限笔记名。
- **只隐藏链接，不隐藏普通文字提及**：正文或代码块里直接写出的名字照常返回（代码块内的 `[[...]]` 不是链接，原样保留，避免破坏代码示例）。
- **"无权"与"不存在"返回同一句话**，只在审计日志里区分 `denied` / `not_found`。
- **`wiki_index`**：按 token 动态生成过滤后的目录树，不直接返回 `首页.md`（首页会列出全部项目）。
- **非 `.md` 文件**（图片、PDF、附件）：v1 不提供。

## D3 传输与凭据安全 — 已定

- 监听地址可配置，默认 `127.0.0.1`，必须显式配置成内网网卡 IP 才对外开放；不默认 `0.0.0.0`。
- TLS：支持直接配置证书，或者在前面放反向代理（例如 Caddy `tls internal`），文档给出示例。
- tokens.yaml 只存 token 的 **sha256 哈希**，明文只在生成时显示一次（`python -m wiki_mcp token-new <name>`）。配置文件泄漏不等于凭据泄漏。
- 开启 MCP SDK 自带的 Host/Origin 校验，防 DNS rebinding。
- 所有工具都按 token 限频，不只是写工具。鉴权失败也写访问日志。
- 只提供扫描得到的 `.md` 文件；用户输入的路径只在可见文档集合里查找，从不拼成文件系统路径。扫描不跟随符号链接与 Windows junction，目录再做一次 `realpath` 是否在根目录内的校验。

## D4 返回内容带时效与状态 — 已定

- 每条结果都带 `mtime`，以及 frontmatter 里的 `status`（如果有）。
- 冻结目录（如 `技术文档/`）在结果里标注「遗留参考，可能过时」。冻结目录列表可配置。

## D5 工具精简 — 已定（v0.1 实现前 4 个）

| 工具 | 回答的问题 | 合并来源 |
|---|---|---|
| `wiki_search(query, limit?)` | 有没有讲 X 的？ | 原 `wiki_search` + `wiki_questions`（问答作为结果类型标签） |
| `wiki_read(path, offset?)` | 这篇具体写了什么？ | 原 `wiki_read` + `wiki_related`（文末附过滤后的出链/反链）；截断后用 `offset` 续读 |
| `wiki_index(path?)` | 这里有什么？ | 原 `wiki_index`，改为动态生成 |
| `wiki_recent(days)` | 最近有什么进展？ | 不变 |
| ~~`wiki_submit(project, kind, title, content)`~~ | 我想问 / 想提需求 | 原 `wiki_ask` + `inbox_write`；随 D1 搁置 |

原则：一个工具对应一类问题，工具之间不重叠，避免 agent 选错。

## D6 支持多种知识库类型：共享核心 + 后端插件，全部在一条主线上 — 已定（v0.1：obsidian、markdown）

目标：除了 Obsidian，也能接其他类型的知识库。

**不按类型开长期分支。** 安全相关的部分（鉴权、scope 过滤、返回预算、审计、收件箱）各类型必须完全一致，分支化之后安全修复要同步到每条分支，迟早漏。各类型真正不同的只有"怎么列、怎么读、怎么搜、怎么解析链接"，这部分做成后端插件，每种类型一个目录，全部合在 master 里。社区贡献新类型就是往 master 提一个后端的 PR。

```
wiki_mcp/
  server.py / access.py / policy.py / service.py / audit.py / config.py
              鉴权、权限判定、链接脱敏、返回预算、审计日志、工具   ← 所有类型共用
  backends/
    base.py       后端接口
    obsidian.py   v1
    markdown.py   v1（普通 Markdown 文件夹，顺便验证接口确实通用）
    logseq.py / siyuan.py / ...   以后
```

后端接口（核心只认这些，不认文件系统）：

- `list()` → 文档条目：`id`、**逻辑层级路径**、标题、`mtime`（可选）、元数据
- `read(id)` → 正文
- `search(query)` → 候选结果（后端有原生搜索就用原生的，没有就由核心做子串扫描）
- `links(id)` → 出链 / 嵌入（每种类型的语法不同：`[[wikilink]]`、相对链接、Logseq 的块引用……）

两条关键约束：

- **权限按"逻辑层级路径"判定，不按磁盘路径。** Obsidian 的层级就是文件夹；Logseq 的页面在磁盘上是平铺的，层级要用 namespace（`项目/风电A/xxx`）表达。由后端负责把自己的结构映射成路径，核心的 scope 判定保持一套。
- **收件箱与后端解耦。** 收件箱始终写在本地文件系统，后端只读。只读的、或者不方便写的知识库类型也能用投递功能。

各类型的优先级：

| 类型 | 特点 | 建议 |
|---|---|---|
| Obsidian / 普通 Markdown | 本地文件，活文件零同步 | v1 |
| Logseq、Foam、Dendron | 本地文件，链接语法和层级不同 | 以后，按需求来 |
| 思源笔记 | 本地，但数据在 SQLite / 本地 API 里 | 以后 |
| Notion、Confluence、语雀、飞书、钉钉文档 | 云端 API，平台自带权限，限流 | **不优先**：平台本身有权限体系，很多已有官方 MCP；本项目的独特价值在"没有服务端的个人本地知识库" |

- 后端的第三方依赖用可选安装（`pip install wiki-mcp[logseq]`），核心依赖保持最小。
- 每个知识库一份配置：后端类型、根目录、硬排除追加、scope 定义、冻结目录、frontmatter 字段名、收件箱位置。个人配置不进仓库，`examples/` 下放各类型的示例配置。
- v1 一个进程服务一个知识库。

## 搁置（以后考虑）

- **可用性**：服务跑在个人电脑上，关机就查不了。需要向同事说明预期，以后再考虑常驻主机。
- **访问日志的隐私**：日志会记录同事查了什么，要在接入说明里告知。
- **中文检索排序**：v1 用子串匹配，排序较弱；等日志显示确实有检索盲区，再考虑分词或 embedding。
